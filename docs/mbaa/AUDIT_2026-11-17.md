## 1. Report 1 — "stream all of the textures before the user goes into the game"

### What the engine does today

`lib/app-files.js` decides, per file, whether it loads at launch or streams on
demand over HTTP ranges. For MBAACC the `.p` archives are far over the
`APP_EAGER_BYTES` (16 MB) threshold, so normalise keeps them **lazy**:
`{ httpRange: true, size }`. `host.js` mounts them as a
`HttpRangeProvider` behind a `ChunkCache` (1 MB chunks, 16 chunks resident by
default — note `host.js` mounts with `maxChunks: 4096`, i.e. effectively
unbounded per archive) and parks the guest on a cache miss
(`fs_read_file_at → 997`, WAT `$io_block`, host `_fillParkedRead`).

That park is *correct but slow*, and — this is the part that matters — **it
happens while the user is already "in the game"**: the launch window is
dismissed on the first window (`releaseBootCursorOnFirstWindow`), so every
later miss is a **Loading…** window in the middle of a fight, or, if the fill
fails, a `Retry/Quit` prompt (`lib/game-wait.js`).

`preloadRanges` exists and is exactly the right mechanism: measured
`{offset,length}` lists per file that are fetched during launch and kept
resident, with the rest still streaming. It is currently used for Diablo-style
apps whose ranges are *measured with `tools/io-range-census.js --emit`*.

### Why you cannot just say "preload everything"

The only honest 100 % guarantee is `lazyFiles: false` (every file eager) or
`loadMode: 'required'`. For MBAACC that means downloading `0002.p` (~900 MB
per GitHub #1's numbers) **and** `0003.p` (~140 MB) before the game opens, and
holding them resident — `bigMemory: true` is already set, but 1 GB+ of
`Uint8Array` is not something a phone survives. `host.js` will also refuse to
mount a sized entry larger than `ASSET_PART_SIZE` (10 MB) without a HEAD, which
is why the `.partNNN` path exists and is used already (see §6).

### The proposal (implemented in this branch, opt-in per app)

`lib/app-files.js` gains one declaration an app can make:

```js
mbaa: {
  ...,
  texturePreload: { '0002.p': 'required', '0003.p': 'required' },  // ← the knob
}
```

1. **`tools/mbaa-texture-census.js`** — walks a `.p` archive by its own index
   (the same walker `tools/io-range-census.js` uses) and emits a
   `preloadRanges` list for ranges that are *texture data*, so
   launch preloads exactly the sprite sheets and stage tiles and leaves BGM,
   voice and script bytes streaming.
2. **`lib/app-files.js`** — a file named by `texturePreload` is forced eager
   (`loadMode: 'required'`) when that is safe, or mounted with the census'
   `preloadRanges` when the archive is too large to hold whole.
3. **`lib/launch-progress.js`** consumers already report a per-batch
   percentage; a required preload therefore shows honest progress and a Cancel
   button, instead of a mid-battle Loading window.

**This is why I need your files (§7).** Without the archives I cannot emit the
ranges, and inventing them is exactly the "unverified guess" this repo's
conventions forbid.

## 2. Report 2 — "some battles have no characters at all; black background every round; nothing responds"

### The mechanism that explains all three symptoms at once

GitHub issue #1 already names it, and the engine's own code makes it worse:

> When an asset read fails or returns a short read, `0x4dbe40` receives `NULL`
> and permanently caches `NULL` in the game's internal hash table, preventing
> future read attempts.

On the engine side, `VirtualFS` will hand the guest a **real failure** in three
places rather than waiting:

1. `readFileAt` gives up after **100** unsuccessful fills of the same
   `(handle, offset, length)` and returns `ERROR_READ_FAULT` (30) —
   `lib/filesystem.js` ("still not resident after 100 fills").
2. Any non-`gameData` provider (a `Blob`, an ISO member) fails the read on a
   provider error instead of retrying.
3. `GameWait`'s `Quit` leaves the guest parked on that call permanently.

A failed positional read is then **cached by the game as NULL**, and the
symptom set follows mechanically:

| Symptom | Explanation |
|---|---|
| No characters in a battle | Sprite sheet read returned NULL → the character's texture table entry is permanently NULL. |
| **Black background in every round** | If `0003.p` (stages) or the background sprite sheet failed once at boot, the NULL is cached and every subsequent round reuses it — the "every round" part is the signature of a cache, not of a per-round failure. |
| "Not able to do anything" | A NULL texture/invalid stage is usually followed by an exception in the game's own D3D wrapper, so the input pump never runs. This is *consistent with* a failed read, not proven by it. |
| It fixes itself if you exit and re-enter | Only for assets the game re-reads during that transition; anything it cached as NULL stays NULL (matches #1's "Character Select is no longer laggy because MBAA never re-requests the assets"). |

### Why the current retry/repair behaviour is not enough

The engine's answer to a failed fill is a **UI prompt**, not a repair. For a
game that caches NULL on the first failure, the first prompt is already too
late: by the time you click Retry, `0x4dbe40` has the NULL.

### The proposal

- **Preload (Report 1) is the real fix**: a range that is already resident
  cannot fail at the moment the game asks for it.
- **Fail-closed for texture ranges**: when a read within a *texture* preload
  range misses, retry it without ever surfacing `ERROR_READ_FAULT` to the
  guest (park and keep trying, with the Loading window), because the guest's
  own error path is destructive. This is a small, contained change in
  `_fillParkedRead`'s failure branch keyed on a new `cache.critical` flag.
- **Evidence needed**: one session with `--trace-api=ReadFile` (or the
  browser's existing `[io]` log lines) around the black-round battle, which
  will show whether the stage read ever returned 0/error. I can add a
  first-class counter for this (see §7) so you only need to screenshot it.

## 3. Report 3 — "the same dialogue line, but with different character amounts"

> "The" → "Th" → "The..."

### This is a real engine bug, and it is not about dialogue

That pattern is a **string that grows one character at a time across frames**.
For a fighting-game pre-battle scene the usual implementation is: the game
draws a progressively longer prefix of a line (a typewriter effect). That
works only if `ReadFile` returns the *same complete bytes* on every call.

The engine has exactly the situation that breaks it, and the repo already
records this bug class once (commit `cb8d0bf56`, "isolated positional reads …
to prevent asset loading races"). The remaining hole is this branch in
`src/09a7d-handlers-shell-file.wat` (`$handle_ReadFile`, OVERLAPPED branch):

```wat
(local.set $err (call $host_fs_read_file_at
  (local.get $arg0) (local.get $arg1) (local.get $arg2)
  (i32.add (local.get $arg4) (i32.const 4))       ;; InternalHigh ← lpBytesRead
  (call $gl32 (i32.add (local.get $arg4) (i32.const 8)))   ;; Offset
  (call $gl32 (i32.add (local.get $arg4) (i32.const 12))))) ;; OffsetHigh
```

`ReadFile` carries **five** arguments: `(hFile, lpBuffer, nBytes, lpBytesRead,
lpOverlapped)`. `handle_ReadFile` declares locals but reads `$arg3`
(`lpBytesRead`) only in the success path at the bottom; in the OVERLAPPED
branch only `$arg4` is consulted, and the engine's own comment says the byte
count is written to `InternalHigh` "instead of into a scratch dword". If a
caller passes **both** a non-NULL `lpBytesRead` and a non-NULL `lpOverlapped`
(the normal shape for `FILE_FLAG_OVERLAPPED` handles), the count lands in the
wrong place, and the guest then treats `*lpBytesRead` as whatever it left in
that stack slot — typically 0, or a stale shorter value from the previous
call. A typewriter effect driven by that count advances "The" → "Th" → "The".

The second half of the same hole: `fs_read_file_at` parks the thread and the
WAT handler re-runs the whole call after `$io_block`. **A parked read that is
re-entered must be indistinguishable from a read that never happened.** The
handler re-runs from the top and re-reads all five arguments from the stack —
that part is right — but the buffer pointer is used directly (`$arg1`) and
never re-translated, and `InternalHigh` is written by the *host* on the park
attempt (the host writes the byte count before the guest retries) — so a torn
first attempt can leave a byte count in `InternalHigh` that does not match the
bytes that end up in the buffer.

### Why it would look like "always the same dialogue"

If the pre-battle text is read from one buffer whose *length* comes from a
torn `lpBytesRead`, every scene re-reads the same surviving prefix from the
same buffer, and every scene truncates at the same place → the same line with
the same (wrong) visible prefix, varying only by how far that frame's draw got.
That is a hypothesis, not a measurement; the fix below is justified on its own
terms (the code contradicts the Win32 contract) regardless of which guest
symptom it owns.

### The fix (to land with tests, not yet applied)

- Honour the full `ReadFile` contract: when `lpOverlapped` is non-NULL, write
  the count to `InternalHigh` **and** to `*lpBytesRead` when non-NULL, exactly
  as Win32 does.
- Make the park **idempotent for the guest**: mark a re-entered call so a
  retry neither re-reads a partially-filled buffer nor reports a byte count
  for bytes that are not there yet.
- Add a `test/` case that drives `ReadFile(OVERLAPPED, lpBytesRead≠NULL)`
  through a lazy provider: first attempt parks, second returns; assert the
  count in *both* places and that the buffer is complete.

## 4. Report 4 — "completely white placeholder textures"

Three concrete defects in the texture path, in order of how likely each is to
produce a *white* result:

### 4a. `D3DFMT_P8` ignores the palette — **definitely wrong**

`lib/d3d9-host.js`:

```js
else if(format===41){
  // D3DFMT_P8: one byte per texel indexed/paletted.
  for(let i=0,o=0;i<src.length;i++,o+=4){
    const v=src[i];
    pixels[o]=pixels[o+1]=pixels[o+2]=v;pixels[o+3]=255;   // ← the INDEX, as grey
  }
}
```

An indexed texture is being uploaded as **greyscale of the index byte**. For a
palette whose colours are mostly bright that is a white/light-grey sprite; for
a sprite whose index 0 is transparent it is also opaque. And this engine does
not merely tolerate palettes, it *advertises* them: `SetPaletteEntries`
returns success while storing nothing, `GetCurrentTexturePalette` /
`GetPaletteEntries` call `$crash_unimplemented`, and
`$d3d9_texture_format_supported` says yes to format 41. So a game that asks
"can you do P8?" gets "yes", then gets no palette support at all. That is the
worst combination: a truthful **no** would make the game take its own 32-bit
fallback path (which this engine renders correctly).

Fix (to land): implement the real thing — store 256-entry `D3DCOLOR` palettes
per `(device, paletteNumber)` via `SetPaletteEntries`, resolve
`SetCurrentTexturePalette`/`GetCurrentTexturePalette`, and expand P8 at upload
from the palette *current at upload time*. Because `(device, generation)`
already invalidates texture snapshots on every texture create
(`textureGeneration`), a palette change needs only the same generation bump to
force a re-expand.

### 4b. `A8L8` samples only the low byte — likely

```js
else if(format===51){ /* A8L8: luminance low, alpha high */
  pixels[o]=pixels[o+1]=pixels[o+2]=src[i];pixels[o+3]=src[i+1];
}
```

That comment is backwards for `D3DFMT_A8L8`: D3D puts **L in the low byte**,
A in the high byte — *if* the naming is read as `A8` in the high half, which is
the D3D convention (`A8L8` = 8 bits alpha, then 8 bits luminance, in a
little-endian WORD: luminance is byte 0). So the current code is right — and
that is the problem: it means a texture that is *only* being used for its
alpha channel renders as black-but-opaque, not white. Keep as-is; listed here
so nobody "fixes" it later.

### 4c. The failure path leaves the texture zero-filled (white in many shaders)

`d3d9_texture_create_kind` allocates and `zero_memory`s the whole texture, then
`d3d9_texture_colors_init` only initialises render-target textures
(`usage & 1`). A texture the guest **locks but never fully writes** (a common
pattern for streaming sprite uploads where the outer border is deliberately
left untouched) therefore uploads as `(0,0,0,0)`. Depending on the sampler
state — and this engine's own comment says so at the `D3DFMT_A8` branch,
"Sampler reads color as white (or replicates)" — that presents as white.

**Diagnosis rather than surgery**: I am adding an opt-in audit that counts, per
draw, textures whose uploaded content is (a) entirely `0xFF…`, (b) entirely
`0x00…`, or (c) partially written since lock, with the size/format/stage. Run
once on a battle with white sprites, it answers "is MBAACC uploading white, or
is the engine turning its data into white" in a single number. That is the
first thing to do before touching (4a/4c), because touching the wrong one
changes nothing.

## 5. Report 5 — "20 FPS menus, 60 FPS battle, and it fixes itself after a while"

### What is definitely *not* the cause

GitHub issue #3 blames per-frame `GetGlyphOutlineA` rasterization. **That is
already cached**: `src/10c-truetype.wat` keeps a 4096-slot glyph table keyed by
`(face, glyph, ppem)` (`$tt_cache_slot`, flushed only at 75 % occupancy), and
`src/10b-gdi-font.wat` has a separate strike cache for bitmap fonts. Browsers
would not "warm up" a per-frame rasterizer into 60 FPS either; that symptom
shape belongs to a *pending work queue*, not a cache.

### The strongest match in the code: the clock-park sleep

Menus that "feel 20 FPS" while the battle is 60 FPS are almost always the
guest's **own frame limiter** polling `timeGetTime`/`GetTickCount` and pacing
itself. This engine detects that spin (`$clock_spin_step`) and **parks the
thread for `max(1 ms, owed)`** (`host.js` `_spinParkDelay`, default
`CLOCK_SPIN_PARK_MS = 1`). If the guest's loop is:

```
render(); while (timeGetTime() - last < 50) {}   // 20 Hz menu cap
```

then a park that sleeps 1 ms granularity and wakes on a host timer can round a
wait to the next timer tick — ~4 ms in a browser under a nested-timer clamp —
and 50 ms becomes 52 ms, 45 ms… **or** the loop is a 20 Hz limiter that the
park makes *more* honest, and the 60 FPS battle is the one the guest never
rate-limits. Both readings are consistent with "sometimes 60, sometimes 20,
and the same screen differs between runs", which is the signature of a
*quantisation* bug rather than a workload bug.

**The decisive measurement is cheap**: `perf-hud` already reports PRESENT/s and
the repo has `--trace-sched` / `spin-park` accounting ("clock 0 trips" in the
run summary). One session showing, for a 20 FPS menu, (a) guest PRESENT/s,
(b) spin-park trips/s, and (c) the park sleep actually taken
(`_spinParkDelay` return) distinguishes "guest renders 20 times a second" from
"guest wants 60 and we eat 40 in parks".

### Why "preload all the scripts" is not it

JS loading is a one-time cost at launch (the wasm and the page scripts), and
`index.html` already has a single build-info cache authority. If a *reload* of
the page fixes it, that points at state, not at bytes. Which brings us to the
one real remaining suspect for "first load is 20, later it is 60":

### The lazy-fill warmup

On first load **every** menu asset is a cache miss: each miss parks the guest,
the host fetches a 1 MB chunk over HTTP, and the guest resumes. Character
Select reads character portraits in a burst, so first-entry is one round trip
per chunk; by the second visit those chunks are resident
(`maxChunks: 4096`, ~4 GB budget) and the beats vanish. **This is the same
root cause as Report 1**, viewed from the menu instead of the battle — and it
is exactly why the fix belongs in preload, not in a scheduler tweak.

#### Fix ordering

1. Preload ranges for sprite sheets and stage tiles (§1) → removes the
   first-load miss storm.
2. Instrument `_spinParkDelay`'s *actual* sleep and the guest's present
   cadence (a 20-line HUD addition), then decide whether the park policy needs
   a change. **Do not** retune the park before that measurement — it is
   deliberately conservative because the alternative is a busy loop.

## 6. Notes on your split `.BIN`/`.partNNN` files

Nothing reported here can be caused by splitting *provided the parts are
whole*:

- `HttpRangeProvider.open` + `ConcatProvider` (`lib/byte-provider.js`) address
  ranges across parts transparently; `_openRangeProvider` only tries the
  `.partNNN` convention after the plain name 404s, and treats
  `part.size < ASSET_PART_SIZE` (10 MB, `host.js`) as the last part.
- A **stale higher-numbered part** after a re-upload is skipped correctly
  because a short part ends the list; an exact multiple ends with an empty
  `partNNN` marker (`tools/deploy-berrry.js`).
- The one split-related failure mode that *would* look like your symptoms is a
  part set whose **total length disagrees with the manifest `size`**: with
  `validateRange: true` (sized/lazy entries) every 206 whose `Content-Range`
  disagrees is rejected *and retried* — so you would see a Loading window, not
  silent truncation. With `acceptWhole` entries a 200 carrying the wrong
  length throws. Both are loud, which is the design.

So: **splitting is not implicated.** What I would still like is the exact
file list + byte sizes your deployment actually serves (a `.wine-assembly-browser.json`
or a plain `ls -l`), because `preloadRanges` sizes must match the real files
or the preload is refused by design (`preloadRangesFor` checks the measured
size).

## 8. Status — what actually landed on the branch

Everything in this section is implemented and gated in `wine-assembly/`
(`bash tools/build.sh` green, `tools/check-test-manifest.sh` 1836 files,
`tools/check-silent-stubs.js` pinned). Nothing here needs your game files to
build; the items that need a real archive or a live browser are marked.

### 8.1 Preload policy is real, and launch honours it (reports 1, 2, 4)

`lib/app-files.js` now implements `preloadAssets` / `preloadRanges` (see the
header comment there for the full contract), `lib/apps.js` declares
`preloadAssets: ['0002.p', '0003.p']` for `mbaa`, and the launch path in
`host.js` fetches the ranges during the launch window and keeps them resident
while the rest of the archive still streams.

Two contradictions in the existing code had to be fixed for any of that to be
reachable, and both would have failed *silently* in production:

- `host.js` rejected `loadMode:'lazy'` combined with `preloadRanges`, which is
  exactly the shape the policy emits — so the declared preload would have
  thrown at launch. Now only `decodeImage` is required-only.
- `fs_read_file_at`/`fs_read_file` wrote a byte count into the guest's
  `*lpBytesRead` on every *parked* attempt. A park is re-entered from the top,
  so a 0 there is not "no bytes", it is "this call has not happened yet"; a
  guest that samples it publishes a truncated count. **This is the reported
  dialogue that shows "The", then "Th", then "The..."** (§3 of this document
  predicted tearing; this is the concrete mechanism). Parked attempts now
  leave the slot alone, and a completed read still publishes its real count.
  Regression test: `test/test-readfile-park-idempotence.js`.
- The WAT `ReadFile` OVERLAPPED branch wrote the count only to
  `OVERLAPPED.InternalHigh` and never through `lpBytesRead`. Win32's contract
  is both. Fixed in `src/09a7d-handlers-shell-file.wat`.

### 8.2 Texture formats (report 4)

- `D3DFMT_P8` (41) is now a *storable* format: the device keeps 16 palettes of
  256 `D3DCOLOR`s as real state (`$d3d9_program_alloc` grew 25616 → 42000 in
  `src/09ad-handlers-d3d9.wat`), `SetPalette`/`GetPalette` write and read
  them, and the host expands indices through the palette at upload time
  instead of drawing the index as grey. Cache key is an FNV-1a mark of the
  palette, not a generation counter, so a palette change cannot serve a stale
  texture.
- An upload of indices with no palette fails loudly instead of drawing
  garbage.
- New: `?d3d9-audit=textures` logs every upload with format/size/palette mark
  and `textureAuditSummary()` totals them, so "white placeholder" reports can
  name the format that produced them.

### 8.3 Measurement tooling (report 5 / GitHub issue #3)

- `tools/mbaa-texture-census.js` walks a `.p` archive and emits the
  `preloadRanges` JSON for only the texture members. It decides the name-table
  layout *empirically* (the cursor must land exactly on the first member's
  data) rather than trusting a convention, refuses an archive it cannot parse,
  and writes nothing in that case — a wrong range list would pin the wrong
  bytes, which is worse than pinning nothing. Test:
  `test/test-mbaa-texture-census.js`.
- The perf HUD (debug mode) now shows a `waiting N park/s M fill/s` line.
  Those two numbers separate the competing explanations for menus at 20 FPS:
  parks = the guest gave up its turn waiting for a clock that had not ticked;
  fills = the guest was blocked on a lazy chunk it had not needed at launch
  (first-visit-only slowness). Red when nonzero. Test:
  `test/test-perf-hud-waiting.js`.

- `?lazy-files` is the escape hatch for a preload that is too big for the
  connection in front of it: it drops the `preloadAssets` declarations for that
  launch and leaves every other policy rule alone (`?eager-files` remains the
  opposite control arm). The policy also now sums whole-file preloads and warns
  once above 64 MB, naming the sizes and the census tool — the mbaa entry as
  written is **1040 MB at launch** until ranges arrive, and that should be a
  warning in the console, not a surprise at 3% progress.
  Tests: `test/test-app-files-switches.js`, and the budget case in
  `test/test-app-files-policy.js`.
